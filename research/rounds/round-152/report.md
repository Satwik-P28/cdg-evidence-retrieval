# R152 native-token equivalence and fair query controls

Status: implemented, unverified. Hypothesis: distinct source bytes may share the same ordered native FTS5 default unicode61 tokens; positional retrieval can share their index representation without merging source identities. The C extension exposes an unambiguous binary length-prefixed token sequence via the public tokenizer API (https://sqlite.org/fts5.html). Compare representative streams exactly after digest lookup, reject colocated synonyms, preserve positions by sequence order. Test against actual fts5vocab instance output, including Unicode, NUL, punctuation, repeats and empty source. No byte offsets or highlighting equivalence. Raw source and evidence are not merged. Existing repetitive indexing and fragment compression prior art: He/Suel https://doi.org/10.1145/2348283.2348319; Universal indexes https://arxiv.org/abs/1604.08897; repetitive document retrieval https://doi.org/10.1007/s10791-017-9297-7. No claim that normalization or sharing itself is new.

Three physical index-only arms: revision, exact raw and exact native-token sequence. Same active-statistics/mapping schema and mapping index, same materialized native phrase match SQL joined directly to active revision identities, same expanded per-revision BM25 scorer (no full ledger scan or snapshot preparation). Three shuffled query repetitions; compare exact native ranks, scores and df; charge complete SQLite bytes. Both frozen AP cohorts, independent CLARK and explicitly synthetic case/punctuation variant stress; no synthetic savings reported as real. No transactional integration in R152. R151's 27.67x latency comparison is confounded by full ledger loading; R152 tests a fairer query path at index level.
