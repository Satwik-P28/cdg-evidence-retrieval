# R140: TimIR native component reproduction

Status: all three original-code jobs passed.

TimIR (ECIR 2025, DOI 10.1007/978-3-031-88717-8_34) and its preceding SIGIR-AP 2024 paper already provide historical sparse retrieval and citation by ranked-list hashes. Pin upstream https://github.com/MoritzStaudinger/TimIR/tree/90df24ba022f18280c30ffcf68fcbd0f4b7685a6. Inspect SearchService, FileService, LuceneConfig and DocumentDaoMonetDB. The native service uses StandardAnalyzer, Lucene 8.4.1 BM25, quantized document norms, historical validity intervals and a MonetDB SQL scorer; result metadata hashes concatenated result names with MD5. Historical source-byte identity and source compression are not provided by that result-name commitment. This observation concerns the inspected code path, not the full possible features of TimIR.

Two independent gates: build unmodified upstream backend using Java 11/Maven; run the exact extracted DAO SQL on actual MonetDB with document/term statistics produced by actual Lucene 8.4.1 StandardAnalyzer and SmallFloat. Minimal adapter supplies stable paths as names and synthetic generation timestamps, no changes to scoring SQL other than parameter binding. Frozen BIPs and Git large histories, 4 cutoffs and up to 72 fixed initial-snapshot single alphabetic terms. Compare native Lucene independently rebuilt active snapshots against final-state MonetDB historical results; repeat and check exact SQL result/hash. Report rank agreement, overlap and score errors rather than forcing equality. No claim of full TimIR service integration, storage or latency parity, or direct FTS5 vs Lucene score equivalence. Docker latest image is recorded by digest in logs; pin successful digest for followup reproducibility. Build failure is a reproduction blocker, not a claim about the published algorithm. 


## Verified results

These are distinct scorer semantics, not directly comparable to FTS5 score errors. Upstream SHA256 SQL fingerprint is in raw results.
